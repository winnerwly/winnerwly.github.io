# AI 编程 workflow：我的高效开发流程分享

用 Trae 做开发有一段时间了，我总结出一套适合自己的 AI 辅助开发流程。这篇文章分享给大家，希望对你有启发。

## 传统开发 vs AI 开发：思维转变

先说说最大的区别：

**传统开发流程**：
```
需求理解 → 架构设计 → 手写每一行代码 → 调试 → 测试 → 上线
```
人要做所有事情，每个环节都靠自己。

**AI 辅助开发流程**：
```
需求理解 → 让 AI 帮你拆解设计 → AI 生成大部分代码 → 人做审查和调整 → 测试 → 上线
```
核心转变是：**你从「代码打字员」变成「产品经理 + 代码审查者」**。

这个转变刚开始可能不习惯，但习惯之后效率提升非常明显。

## 我的 AI 开发完整流程

我现在做一个新功能，基本是这么个流程：

---

### 第一步：需求拆解 —— 先想清楚再动手

**做什么**：拿到需求后，先让 AI 帮你拆解一下。

**怎么用 Trae 做**：

```
/plan
我需要开发一个用户注册登录功能，包含：
- 邮箱注册验证
- 密码登录
- JWT token 认证
- 忘记密码重置

请帮我拆解一下实施步骤。
```

AI 会给你输出一个类似这样的计划：

1. ✅ 设计数据库表结构
2. ✅ 编写认证中间件
3. ✅ 实现注册接口
4. ✅ 实现登录接口
5. ✅ 实现密码重置接口
6. ✅ 添加错误处理
7. ✅ 添加测试用例

**为什么要这一步**：
- 避免做着做着发现漏了需求
- 可以先确认方案对不对，避免返工
- Large 任务拆解成小任务，好推进

**我的经验**：不管需求多小，先拆解再动手，花 5 分钟省几小时。

---

### 第二步：架构设计 —— AI 帮你出方案

拆解完任务，接下来是设计。这一步不要直接让 AI 写代码，先看方案。

**怎么用**：

```
现在我们来设计用户认证功能的架构。
项目用 Node.js + Express，数据库用 MySQL。
请帮我设计：
1. 数据库表结构
2. 目录结构
3. 核心接口定义
```

AI 会给出设计方案，包括 SQL 建表语句、目录结构、接口函数签名等。

**这一步人要做什么**：
- 看看设计是否符合现有项目架构
- 是否遵从了项目已有的代码风格
- 有没有引入不必要的依赖
- 安全性考虑够不够（比如密码存储）

**一个检查点**：如果 AI 设计的和你项目现有的风格差异太大，可以告诉它：「请按照项目现有代码风格重新设计」。

---

### 第三步：逐个实现 —— AI 写代码，人来审

方案确认后，就开始编码了。建议**一个任务一个任务来**，不要一次性让 AI 写完全部功能。

**我的做法**：

> 我们先来实现第一步：创建用户表的迁移文件。请按照刚才的设计生成代码。

AI 生成完代码之后，**一定要逐行过一遍**：

- [ ] 逻辑对不对？
- [ ] 有没有符合项目编码规范？
- [ ] 有没有安全问题？
- [ ] 注释清楚吗？
- [ ] 错误处理了吗？

没问题就接受，有问题就告诉 AI 哪里要改。

```
这个地方有个问题：密码应该用 bcrypt 哈希存储，不要明文存。请修改一下。
```

**为什么要逐个来**：
- AI 上下文有限，一次做太多容易错
- 一步一步验证，错了早发现
- 保持思路清晰

---

### 第四步：调试排错 —— AI 帮你定位问题

运行出错了怎么办？传统方式是自己看日志猜，现在可以让 AI 帮你分析。

**正确的提问方式**：

```
我调用注册接口的时候返回 500 错误，日志在这里：

[粘贴错误日志]

请帮我分析一下可能是什么原因？
```

如果错误信息不够，可以说：

```
帮我看看这个文件的第 45 行，这里可能有什么问题？
```

**我的经验**：AI 排错比人快很多，尤其是那些语法错误、依赖问题、常见坑，AI 一眼就能看出来。但如果是业务逻辑错了，你得告诉它正确逻辑应该是什么样。

---

### 第五步：Code Review —— 让 AI 先帮你审一遍

自己写完（其实是 AI 生成）代码，自己审完一遍，还可以让 AI 再帮你审一遍。

```
帮我 review 一下这个文件的代码，看看有没有什么问题：
- 有没有潜在 bug
- 性能问题
- 安全问题
- 可以重构优化的地方
```

AI 经常能找出一些你忽略的问题，比如：
- 没有处理空值
- 内存泄漏
- SQL 注入风险
- 重复代码
- 不符合最佳实践

---

### 第六步：测试文档 —— AI 一起帮你做了

功能做完了，测试用例和文档也可以让 AI 帮你写。

```
帮我为这个认证模块生成单元测试，用 Jest 框架。
覆盖主要的成功和失败场景。
```

```
帮我写一下这个接口的使用说明，包括请求参数、响应示例、错误码说明。
```

这部分工作 AI 做的相当不错，能帮你省不少时间。

## 人 vs AI：分工协作表

这么多步骤，哪些该让 AI 做，哪些该人做？我整理了一张表：

| 环节 | AI 擅长做什么 | 人要负责什么 |
|------|--------------|------------|
| 需求拆解 | 把大需求拆成小任务，列出步骤 | 拍板：需求范围对不对，优先级对不对 |
| 架构设计 | 出初步方案，给出代码结构 | 判断：符合现有架构吗？技术选型对吗？ |
| 编码实现 | 生成样板代码、CRUD、重复代码 | 审查：AI 写的对不对？业务逻辑正确吗？ |
| 调试排错 | 根据错误日志定位常见问题 | 决策：这个问题根源是什么？方案接受吗 |
| Code Review | 找常见问题、最佳实践违反 | 最终把关：这个合并到底合不合？ |
| 测试文档 | 生成测试用例、接口文档 | 补充业务场景，验证测试覆盖 |

**核心原则**：**AI 负责「产出初稿」，人负责「做决策和把关」**。

## Plan/Spec 模式什么时候用？

Trae 提供了 `/plan` 和 `/spec` 两个命令，什么时候用？

**用 `/plan` 的场景**：
- 新功能开发
- 重构
- 改 Bug 范围比较大
- 需要多步骤实施的任务

**用 `/spec` 的场景**：
- 需求比较复杂
- 需要和产品经理确认细节
- 多个开发者协作
- 要写详细的接口规格

**简单需求**：比如改个文案、调个样式、修个小 Bug，直接让 AI 改就行，不用走 plan。

## 实战案例：添加一个功能全流程走一遍

我们用一个真实小例子走一遍：

**需求**：给博客添加一个「相关文章」功能，显示在文章详情页底部。

### Step 1：Plan

```
/plan 给 Hexo 博客 Chic 主题添加相关文章功能，需求：
1. 在文章详情页底部显示最多 4 篇相关文章
2. 根据标签匹配来找相关文章
3. 如果没有相关文章就不显示
4. 样式要和现有主题风格一致

请帮我拆解步骤。
```

AI 输出：
1. 修改主题配置文件，开关相关文章功能
2. 修改文章模板，添加相关文章区域
3. 实现相关文章匹配逻辑（按标签）
4. 添加样式
5. 测试验证

没问题，确认开始。

### Step 2：设计

```
请帮我设计具体实现方案：
- 配置文件加什么字段
- 模板改哪个文件
- 相关文章逻辑在哪里实现
- 样式怎么加
```

AI 给出具体方案，你看看是否符合现有代码结构，确认。

### Step 3：逐个实现

```
第一步，先修改 _config.yml 添加配置开关，请帮我修改。
```

AI 修改完 → 你审查 → 没问题继续。

```
第二步，修改文章模板 EJS，添加相关文章 DOM 结构。
```

AI 修改完 → 审查 → 继续。

以此类推，一步一步完成。

### Step 4：测试

本地运行看看效果，有问题让 AI 调样式修复。

整个过程下来，原来可能要半小时找文件看结构，现在十几分钟就做完了。

## 效率提升小技巧

最后分享几个我常用的小技巧：

### 1. 告诉 AI 你的项目风格

```
请按照项目现有的代码风格来写，使用 2 空格缩进，分号结尾。
```

提前说清楚，少返工。

### 2. 遇到问题先搜再问

```
search 帮我找一下项目中哪里处理了标签相关逻辑？
```

让 AI 先找到已有代码，再改，不容易错。

### 3. 善用撤销和对比

AI 改完如果不对，直接撤销就行了。多试几个方案，选最好的。

### 4. 保持每次改动小而聚焦

一次改一个地方，比一次改十个地方好。容易验证，错了好回滚。

### 5. 复杂问题拆成多篇对话

如果任务太大，一次上下文装不下，可以拆成多次对话。做完一部分保存提交，再开新对话做下一部分。

## 总结

我的 AI 开发 workflow 总结起来就是六句话：

1. **先规划后编码** —— `/plan` 先拆任务
2. **先设计再实现** —— 方案确认了再写代码
3. **小步快跑** —— 一次做一点，做完验证了再继续
4. **AI 出力，人把关** —— AI 生成初稿，人做最终决策
5. **善用工具** —— Skill 和代理该用就用
6. **持续迭代** —— 慢慢找到适合自己的节奏

这个流程不一定适合所有人，但可以作为你摸索自己流程的起点。AI 时代，找到适合自己的协作方式，效率提升真的很大。
