# 怎么给 AI 定规矩

用 AI 写代码，有时候它聪明得像读了你心思，有时候又像第一次来——不读你的代码风格、自己加功能、改 bug 顺手把你半个文件重构了。

很多人这时候会怪 AI 笨。但我用得越久越觉得：**问题多半不在 AI，在于你没给它立规矩。**

AI 默认是按「通用最佳实践」干活的，可你项目里那套约定、你个人的偏好、这次任务的边界，它统统不知道。你不告诉它，它就自己猜，猜错了你生气。

这篇文章就讲一件事：**怎么给 AI 编程助手定规矩，让它听话又靠谱。**

## 一、先说为什么要定规矩

不定规矩，AI 就凭「直觉」干活，而它的直觉是全网代码的平均值——不一定适合你的项目。

举几个真实场景：

- 你让它**加个字段**，它顺手把整个文件的命名风格从驼峰改成了下划线，因为它觉得「更规范」
- 你让它**修个 bug**，它修是修了，还顺手加了个它认为有用的日志、改了点它觉得不顺眼的代码
- 你让它**写个函数**，它用了项目里根本没装的库，或者用了和你现有代码完全不一致的写法
- 你让它**改一处**，它改了三处，另外两处你根本没让它动

这些都不是 AI 在捣乱，是它在「好心办坏事」。**规矩的作用，就是把你的偏好、项目约定、任务边界，提前告诉它，让它别瞎发挥。**

一句话：**规矩不是限制 AI 的能力，是给它一个框，让它在这个框里发挥。**

## 二、规矩写在哪——四种载体

给 AI 定规矩，不是只能在一个地方写。按作用范围从大到小，有这么几种：

| 载体 | 作用范围 | 谁生效 | 适合放什么 |
|------|---------|--------|-----------|
| 系统提示词 / 自定义指令 | 个人级，跨所有项目 | 只你自己 | 个人偏好、通用习惯 |
| 项目规则文件 | 项目级，团队共享 | 所有用这个项目的人 | 项目约定、架构规则、流程要求 |
| 单次对话的 prompt | 任务级，临时 | 仅本次对话 | 这次任务的具体要求 |
| 代码注释 / docstring | 局部，针对某段代码 | 改到这段代码时 | 这段代码的特殊约束 |

一个个说。

### 1. 系统提示词 / 自定义指令：你的「个人底色」

这是跨项目生效的，讲的是「你这个人写代码的习惯」。比如：

- 我偏好用 TypeScript，能加类型就加类型
- 注释用中文，代码用英文
- 变量名要语义化，别用 `a`、`b`、`tmp`
- 回答简洁，别一上来一长篇

这类偏好放在系统提示词里（Claude 的 custom instructions、Cursor 的 rules for AI、ChatGPT 的自定义指令），所有项目都生效，省得每次重复说。

### 2. 项目规则文件：团队的「项目宪法」

这是最重要的一种。它是一份放进项目仓库的文件，告诉所有人和所有 AI：**这个项目长什么样，代码该怎么写，事情该按什么流程走。**

不同工具叫法不一样：

- Claude Code 用 `CLAUDE.md`，也支持 `AGENTS.md`
- Cursor 用 `.cursor/rules` 或 `.cursorrules`
- GitHub Copilot 用 `.github/copilot-instructions.md`
- Trae 也有自己的项目规则配置

内容上一般放：

- 项目结构（哪个目录放什么）
- 技术栈和版本
- 代码规范（命名、缩进、文件组织）
- 架构约定（结构改哪里、视觉改哪里、行为改哪里）
- 开发流程（比如改代码前要不要先写文档、要不要确认）

我们项目里就有一份 `AGENTS.md`，把「先分析、再文档、经确认、后开发、再总结」这套流程写得明明白白。AI 一进来读完，就知道这个项目不能上来就改代码。**这就是规矩的价值——一份文件，让 AI 自动对齐团队流程，不用你每次口头交代。**

### 3. 单次对话的 prompt：这次的「临时要求」

有些规矩是这次任务特有的，不用沉淀成项目规则。比如：

- 「这次只改这一个函数，别动别的」
- 「先别写实现，给我三个方案对比」
- 「用我这边的工具函数 `formatDate`，别自己造」

这种写在当次对话里就行，任务结束就失效。

### 4. 代码注释 / docstring：局部的「贴条提醒」

针对某段代码的特殊约束，直接写在代码旁边最有效。比如：

```ts
// 不要在这里加副作用逻辑，这个函数必须保持纯函数
// 改这里之前先看 xxx 模块，两边有联动
function computeScore(input: ScoreInput): number {
  // ...
}
```

AI 改到这段代码时，会自动读到这条注释，比让它去翻规则文件靠谱。

## 三、规矩怎么写才管用——六条原则

知道写在哪了，更关键的是**怎么写**。写得模糊，AI 照样乱来。我总结了六条：

### 1. 具体胜过空泛

这是最重要的一条。

❌ 「写高质量代码」「遵循最佳实践」「代码要规范」

这些话等于没说，AI 心里的「最佳实践」和你心里的不一定一样。

✅ 「用 2 空格缩进」「函数名用小驼峰」「每个公开函数加 JSDoc」「错误用 `Result` 类型返回，不要 throw」

**能复述成可检查的标准，才算规矩。**

### 2. 既要说「做什么」，也要说「不做什么」

AI 容易过度发挥，所以边界要画清楚。

✅ 「只改 `user.ts` 这个文件，不要动其他文件」「加这个字段就行，不要顺手重构」「修这个 bug，不要加新功能」

告诉它别做什么，往往比告诉它做什么还重要。

### 3. 给正反例

AI 看例子比看抽象描述准。能用例子说明的，就给例子：

```ts
// ✅ 正确
const userList = await fetchUsers();
const activeUsers = userList.filter(u => u.isActive);

// ❌ 错误：不要用缩写，不要用 var
var ul = await fetchUsers();
var au = ul.filter(u => u.isActive);
```

一对正反例，胜过十句「命名要清晰」。

### 4. 分层，别全堆一起

把规矩按层级分开：通用偏好放系统提示词，项目约定放规则文件，临时要求放当次 prompt。

别把所有东西都塞进一份规则文件——文件太长 AI 会读不完，重点会被淹没。

### 5. 可执行、可验证

好规矩是能被检查的。写完一条规矩，问自己：**AI 做完之后，我能一眼看出它有没有遵守？**

- 「代码要规范」——没法验证，废规矩
- 「函数不超过 50 行」——能验证，好规矩
- 「注意性能」——没法验证
- 「列表渲染要加 key，避免用 index 做 key」——能验证

### 6. 保持一致，别打架

规矩之间不能矛盾。比如一边写「优先用函数式风格」，一边又在例子里全是 class，AI 就会懵。

写完规则文件通读一遍，把矛盾的地方理顺。

## 四、一个最小可用的规则文件长啥样

给个简单例子，你可以照着改：

```markdown
# 项目规则

## 技术栈
- 前端：React + TypeScript
- 状态管理：Zustand
- 样式：Tailwind CSS

## 代码规范
- 用 2 空格缩进
- 组件用函数式，不用 class
- 文件名用 kebab-case，组件名用 PascalCase
- 每个 props 都要标类型，不要用 any

## 改动边界
- 只改动的功能，不要顺手重构无关代码
- 改公共组件前先在对话里说一声
- 涉及接口改动，先改类型定义再改实现

## 不要做的事
- 不要自作主张加新依赖
- 不要改 package.json 的版本号
- 不要删现有注释，除非它明显过时
```

就这么点东西，已经能挡掉一半的「AI 瞎发挥」。不用写多，写准就行。

## 五、常见的坑

用规矩用多了，这几个坑几乎人人踩：

**1. 规矩太多，AI 记不住**

规则文件写了几千字，AI 根本读不完，关键规则被淹没。**规矩宜精不宜多**，一份规则文件控制在能让 AI 一次读完的长度，没用的及时删掉。

**2. 太模糊，等于没说**

「写优雅的代码」「注意可读性」——这种话写了跟没写一样。要么改成具体标准，要么删掉。

**3. 规矩之间打架**

一边说「函数要短小」，一边又规定「一个文件只能有一个函数」——AI 不知道听哪条。定期通读，把矛盾的理顺。

**4. 写了就不迭代**

项目在变，规矩也得跟着变。旧规矩过时了不删，新踩的坑不补，规矩文件就慢慢成了摆设。

**5. AI 没遵守就骂它笨**

很多时候不是 AI 笨，是你没写清楚。AI 没按你预期的来，先想想：**这条要求我写进规矩了吗？写得够具体吗？** 大概率是没写，或者写得太虚。

## 六、怎么让规矩越来越好用

规矩不是写一次就完事，得靠迭代。我有个习惯，分享给你：

**每次 AI 犯错，问自己一句：这条该不该写进规矩？**

- 该写 → 加进对应的规则文件
- 不该写、只是这次特殊情况 → 下次口头说就行

这样规矩会随着你的使用越来越准，AI 也会越来越顺手。相当于你在「训练」一份只属于你和这个项目的规则集。

另外，定期做两件事：

- **删**：过时的、重复的、太虚的，删掉
- **合并**：散落在多处的同类规则，归到一起

规矩越精炼，AI 执行得越准。

## 总结

给 AI 定规矩，说到底就三句话：

> **把你的偏好告诉它（系统提示词），把项目的约定告诉它（规则文件），把这次任务的边界告诉它（prompt）。**

写规矩的时候记住六个字：**具体、有界、可验**。

- 具体：别写「好代码」，写「2 空格缩进、函数不超 50 行」
- 有界：告诉它别做什么，比告诉它做什么还重要
- 可验：写完问自己，AI 做完我能不能一眼看出它遵守了没

规矩不是越多越好，是越准越好。**一份写得准的规则文件，顶你十次口头交代。**

AI 不会读心术，但它会读你写的规矩。规矩立好了，它就从一个「聪明的陌生人」变成「懂你项目的老搭档」。
